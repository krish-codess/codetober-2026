# Data profile

Generated by `uplift profile <file>` on the two raw files the system ingests. The tables are tool output; the
findings above each are what the profile changed about the design.

## What the real file told us before any schema existed

The Hillstrom "MineThatData" e-mail challenge file is a randomized experiment: 64,000 customers who bought in the
last twelve months, split evenly across a men's e-mail, a women's e-mail and no e-mail, with visit, conversion and
spend observed over the following two weeks.

| Finding | Evidence | Consequence |
|---|---|---|
| **There is no customer key.** | 12 columns, none an id; 6,562 rows are exact copies of an earlier row. | Those copies are different customers who look alike, not duplicates. De-duplicating would silently delete 10% of the experiment. A file without `customer_id` gets one unit per line (`<sha8>-<line>`); only a file that carries a key is de-duplicated. |
| Three arms, 2:1 treated. | 21,387 / 21,307 / 21,306. | Treatment is "any e-mail" vs none. The expected treated share is 2/3, and training checks the observed share against it (sample-ratio test) before fitting anything. |
| There are no timestamps. | No date column. | The split cannot be temporal for this file; it is a hash of the unit id. When a file does carry `assigned_at` (the synthetic one does) the split is temporal. |
| `history` is floored. | 7,947 rows are exactly 29.99, the minimum. | It is a censored value, kept as is. The generator reproduces the floor. |
| `history_segment` is `history`, binned. | 7 levels that are ranges of `history`. | Not a feature: it adds nothing and would double-count. Kept in the raw file only. |
| `zip_code` says `Surburban`. | 28,776 rows. | The source's spelling is the domain value. "Suburban" is rejected, not corrected, so a silent upstream "fix" is noticed. |
| Conversion is rare. | 578 conversions (0.9%), 9,394 visits (14.7%). | The default outcome is `visit`. A 0.9% outcome on 13k held-out rows cannot rank models; `conversion` and `spend` are supported but not the default. |
| Outcomes are nested. | No conversion without a visit, no spend without a conversion. | Only the chosen outcome column is ever loaded; the other two cannot leak into features because they are never read. |
| The file is clean. | No blanks, no row the contract rejects. | The real file cannot exercise quarantine. The synthetic one must, with the same shape. |

## What the synthetic file adds

Same columns and marginals (control visit rate 10.5% vs 10.6%), plus `customer_id`, `assigned_at`, the true effect,
and the defects a production feed has. Every defect is counted by the generator in `synthetic_manifest.json`, and
`tests/test_ingest.py` and `tests/test_pipeline.py` assert ingestion catches exactly those counts.

| Defect | In the file below | What ingestion does |
|---|---|---|
| Missing features | blank `history` 5,981, `zip_code` 4,024, `channel` 3,094, `recency` 1,992 | Loaded with NULL; the model imputes. |
| Inconsistent formats | `web`/`PHONE`, `$1,234.50`, `Y`/`N`, `01/31/2026 10:00:00` | Normalised to one spelling. |
| Impossible values | recency -1 or 99, history -50.00, `Test E-Mail`, `not-a-date` | Quarantined with a reason and the raw row. |
| Exact duplicate rows | 2,025 | One kept, the rest quarantined as `duplicate_row`. |
| One customer in two arms | 389 customers, 778 rows | All copies quarantined as `conflicting_duplicate`: neither can be trusted. |
| Late outcomes | 3,010 rows with blank outcomes | Quarantined as `missing_outcome`; loaded when `synthetic_late.csv` delivers them. |
